# Bean Backend Backlog

**Reviewed:** 2026-10-19
**Current phase:** finish release-critical configuration, security, and verification. **Sales and HR management routes are the next product phase** after the release gate below.

## Release-critical foundation

### Configuration and process lifecycle

- [x] Declare `pg` and `bcrypt` as backend runtime dependencies and update the backend lockfile.
- [x] Remove the vulnerable `nodemon` watcher chain and use Node's built-in `--watch` mode (Node 20+).
- [x] Add startup validation for database settings, session secret, environment, ports, cookie mode, and exact `APP_ORIGINS` entries.
- [x] Support a TLS-verified Neon `DATABASE_URL` while retaining local `DB_*` configuration.
- [x] Document environment setup in `.env.example`; bind to an explicit host and port.
- [x] Handle `SIGINT`/`SIGTERM` by closing the HTTP server, PostgreSQL session store, and database pool.
- [ ] Validate clean startup and graceful shutdown against the local PostgreSQL database.
- [ ] Create a Neon project, configure the pooled `DATABASE_URL` in local secrets, and verify a connection without committing the URL.
- [x] Resolve the three high-severity advisories reported by `npm install`; they came from `nodemon`'s `chokidar`/`braces` dependency chain. `npm audit --offline` reports zero vulnerabilities after removing that chain.

### Authentication, sessions, and authorization

- [x] Regenerate the session ID before assigning `userId` and `authenticatedAt`, then save the session.
- [x] Reload the current active user for protected requests; reject and destroy sessions for expired, deleted, or disabled users.
- [x] Return safe identity fields and do not cache role permissions in the session.
- [x] Apply explicit authentication and permission checks to inventory and audit routes; keep health routes intentionally public.
- [x] Validate signup/login object shapes, normalize email, bound password bytes, and keep login failures generic.
- [ ] Add database unique constraints for normalized email and username, and verify existing role/permission relationships with migrations.
- [ ] Add integration coverage for signup/login, session fixation, logout, expiration, disabled users, `401`/`403`, and live permission changes.

### Browser and request security

- [x] Enforce exact unsafe-request Origin checks and credentialed CORS for the `APP_ORIGINS` allowlist. Wildcard origins are rejected.
- [x] Enable Helmet and request body limits (JSON 100 KB, URL-encoded 10 KB).
- [x] Add request IDs, a final Express error handler, generic unexpected-error responses, and redacted error logs.
- [x] Remove request-body and audit-record contents from routine logs.
- [ ] Normalize all route-level error responses to the common error shape and stable codes; several validation/conflict responses still use the older `{ message }` shape.
- [ ] Add tests for allowed/blocked origins, credentialed CORS, preflight, missing Origin, body-size limits, security headers, and error redaction.

### Inventory and audit safety

- [x] Use explicit inventory response/query columns and parameterized SQL.
- [x] Keep inventory writes and their audit entries in one transaction; roll back failures before returning.
- [x] Do not fail a successful inventory read solely because its optional read-audit write failed.
- [x] Remove the race-prone duplicate-SKU precheck from create validation and map database unique violations to `409`.
- [x] Validate/coerce inventory create and update fields with bounded types and lengths.
- [ ] Add/verify a database unique constraint for SKU; the application can only prevent concurrent duplicates if this constraint exists.
- [ ] Add migrations for inventory constraints and indexes; inspect existing duplicate data before applying the SKU constraint.
- [ ] Define and test audit field redaction, request/actor metadata, and audit retention. Audit rows currently contain old/new record snapshots.
- [ ] Test inventory pagination, validation, concurrent duplicate SKU, response allowlists, and transaction rollback.

### Idempotency and release checks

- [ ] Define idempotency for every mutating endpoint. `POST /inventory/add` needs per-user/route/key replay and `409` for a key reused with a different payload.
- [ ] Add idempotency storage and transaction-safe concurrent retry handling through migrations.
- [ ] Define whether failed requests release an idempotency key or record a retryable result.
- [ ] Replace the placeholder test script with repeatable automated tests and an isolated test database.
- [ ] Add CI checks for tests, lint, dependency audit, secret scan, migrations, and `git diff --check`.
- [ ] Run a secret scan on the working tree and intended publication history. The current checkout previously had no usable commit history, so history scanning still needs a repository with commits.
- [ ] Verify production cookie settings, approved origins, body limit, security headers, safe responses/logs, and clean graceful shutdown.

## Next product phase: Sales and HR management

Start route implementation after the release-critical test/security gate is met. Build each module with its own permission matrix, migrations, validation, services, audit policy, and tests. Do not reuse the development role as a production authorization policy.

### Shared design decisions before either module

- [ ] Decide whether this is single-company or multi-tenant. If multi-tenant is planned, define tenant scoping before adding business tables or routes.
- [ ] Define role/permission names and least-privilege role bundles for sales staff, sales managers, HR staff, HR managers, and administrators.
- [ ] Choose common pagination, filtering, sorting, error, and audit conventions.
- [ ] Add migrations and seed data for new permissions; use the exact permission names in `requirePermission` and the database.
- [ ] Define data retention, export, backup, and deletion requirements for business and employee records.

### Sales module scope

- [ ] Agree on sales workflow and entities: customers, products, quotes, orders, order lines, and status transitions.
- [ ] Define inventory reservation/decrement timing, transaction boundaries, cancellation, returns, and stock reconciliation.
- [ ] Define payment integration boundaries. Store payment-provider references only; do not store raw card data.
- [ ] Specify ownership rules, customer/contact data access, manager overrides, and audit events.
- [ ] Add protected routes and permissions for customer, quote, order, and reporting operations.
- [ ] Test permission boundaries, validation, concurrent stock changes, order/audit transactions, pagination, and status transitions.

### HR module scope

- [ ] Agree on employee lifecycle and entities: employee profile, department, position, employment status, and any approved leave workflow.
- [ ] Classify employee PII and compensation data; restrict sensitive fields and endpoints to specifically authorized HR roles.
- [ ] Define which employee data ordinary managers may see, retention/deletion rules, and access-audit requirements.
- [ ] Keep payroll out of the first route set unless its legal, privacy, and provider requirements are explicitly designed.
- [ ] Add protected routes and permissions for employee directory, profile changes, departments, and approved HR workflows.
- [ ] Test cross-role access, sensitive-field redaction, audit trails, lifecycle transitions, and tenant isolation if applicable.
